# 工作台验收记录（2026-09-27）

## Codex 实际画布往返与两人灰测判定（2026-09-27）

另起 Codex CLI 会话，仅以“想做一篇高考毕业后留学的小红书图文”作为普通业务需求启动。Agent 先追问国家、路径、受众与目标；用户补充“面向高考后考虑日本本科的学生和家长、三页、清晰轻快”后，才调用只读素材 MCP。检索到的两项候选供逐项取舍；用户保留一项、排除一项后，Agent 读取保留素材，生成三页制作单。首次词库预检命中三处；修改制作单后重扫为零命中，导出四个文字节点与全部连线的逐页 Canvas 交接。

在用户现有 Chrome 无限画布中，实际放置并连接第一页的标题、正文、画风和最终指令四个文字节点；生成配置确认收到四个提示词，配置节点自身提示词留空。第一页成功生成完整有字海报，内容与信息层级基本可用。回传该图至同一 Codex 会话后，Agent 实际读图，指出蓝色书本上的装饰小字含糊及底部提示在手机端偏小，并给出对应单图的发布文案草稿。可辨认文字与文案词库扫描零命中；因装饰字不清，记录为 `textReadability: unclear`，没有提交或批准终稿。

第二页四节点和连线已核对，画布生成在同模型重试、降低分辨率以及换模型后仍失败；错误信息含上游 HTTP 524 超时。该失败不能证明工作台制作单结构有误，但真实任务因此停在一张成品图，三页交付、换图复审、最终归档和员工独立安装仍未实机通过。本版达到**两人受控灰测**门槛，不标记为完整链路正式验收。灰测分别核对员工 Reader 权限、客户端技能和 MCP 加载、无需开发者解释的 Canvas 操作、回图复审及故障后的续做。

## Codex 与 WorkBuddy 同目录计时试验（2026-09-27）

本轮在同一 `xhs-ad-workbench/` 项目目录模拟“做一套日韩留学的小红书图文”，随后用同一澄清口径继续：比较日本与韩国本科留学申请准备时间线，面向高二学生家长，制作三页；现行课程、品牌和价格依据缺失时标待核。以下是**客户端整轮墙钟**，不含模拟用户回复的等待时间；不能把整轮直接归因给模型或 Teedy。

| 阶段 | Codex CLI | WorkBuddy AI 5.6.2（Deepseek-V4.1-Flash） |
| --- | ---: | ---: |
| 模糊需求 → 澄清 | 50.042 秒，正确追问，无素材调用 | 超过 10 分钟仍“准备中”，在 10 分 21 秒由测试者停止；无澄清回复 |
| 明确需求 → 历史候选 | 首次 45.046 秒发现工作台 MCP 未配置；临时接入同一只读 MCP 后，自动审核重试轮次 150.612 秒，展示 4 项图文候选 | 未进入此阶段，不可测 |
| 离线模拟参考全排除 → 三页制作单 | 模型生成 100.068 秒；本地 `sheet` 校验及 990 条词库预检 0.106 秒，三页通过、预检 0 命中 | 未进入此阶段，不可测 |

Codex 成功检索轮次有 4 次 `search_materials`，下载调用为 0；底层 Teedy HTTP 请求数、各次 MCP 耗时与模型等待的可靠分段不可观测。第一次真实工具尝试被 CLI 非交互审批策略拦截；成功轮次用 Codex 的自动审核模式和临时 MCP 配置，未改全局 Codex 配置。WorkBuddy 试验前已把用户级安装的工作台技能、素材技能和只读 MCP 代码同步到此项目版本，哈希校验一致；首轮初期界面显示“正在连接 MCP 服务（3/4）”，之后一直“准备中”，没有可见工具调用，也没有生成本地任务文件。现有证据只能定位到 WorkBuddy 首轮启动／准备阶段，不能断言具体卡点或给出两端同阶段性能比。

用户要求用**真实 MCP 返回的素材**继续制作单后，Codex 从上述 4 项候选中以测试角色保留 1 项、排除 3 项；这不是实际业务用户审批。`get_material` 只读整轮 62.054 秒，返回摘要、标签和 5 张图片元数据，没有正文。只对保留项下载首张图（654,559 字节）并读图，整轮 88.171 秒；另用本机图片查看工具独立核对了版式。Codex 据此生成三页结构化制作单整轮 113.536 秒，引用该真实保留文档，只借鉴已读首图的信息层级，未引用原图不适用的“高考后”时间起点及具体分数/服务事实。`init/candidates/select` 合计 0.179 秒；`sheet` 保存、校验和 990 词预检 0.111 秒，首次命中 1 项；修改测试草稿后重扫 0.069 秒、0 命中。明确需求后的主动步骤合计 **414.732 秒**，MCP 可观察调用 6 次。其余四张参考图未读，不能称作完整文档通读；没有 Canvas 成品和终稿交付阶段。完整证据见本机忽略目录的 `real-full-chain-timing.json`。

原始计时和事件在本机被 Git 忽略的 `runs/benchmarks/codex-trial-20260927-01/` 与 `runs/benchmarks/workbuddy-live-root-20260927.json`。完整真实素材候选仅在本机证据目录，不进入公开仓库。本试验未批量下载、运行付费画布或批准终稿。

## 本轮本地改动与验证

- A：启动需求由 Agent 按业务范围、问题、受众与目标判断是否足以检索，不再把“日韩留学”测试词写死为代码或 Agent 特例；技能与说明采用四次线性交接。用户已撤销本工作台的 `$素材库MCP` 触发词门槛：需求明确、历史参考有用时可直接调用已配置的只读 MCP。Codex 的模糊词实测正确追问；新版 WorkBuddy 仍需人工复核。
- B：只读 MCP 默认取 12 项可调候选池、单次上限 20，展示数量由 Agent 根据实际命中和相关性决定，约五项只是软建议；每项至多一张预览。纯关键词跳过标签列表，移除预探测和无结果回退，明确范围由 `required_concepts` 保持组间 AND/组内 OR。离线假客户端测试覆盖视频带封面仍排除、硬条件、无静默放宽、弹性候选与请求数；未调用真实 Teedy，无法报告优化前后实际耗时或相关性。
- C：用户在无限画布截图中发现上一版制作单同时要求“保留 Logo／生成标题”与“不出现 Logo／文字”，生成了无字背景。新版每页只维护一份精确图上文案，加画风、布局和按需 Logo/参考图；导出器自动拆出标题、正文、画风、最终指令节点与全部连线，保存到 `runs/tasks/<任务ID>/canvas-sheet.md`，不再要求人工同步几份相同文案。画布源码只读核对确认：配置节点编辑提示词为空时会汇总全部已连上游节点，非空时只收显式 `@` 引用，因此交接明确要求前者。用真实 MCP 来源的三页测试制作单重组为简化版并保存，三页通过业务校验和 990 词预检、0 命中；之后又完成了上节记录的第一页付费生图及回图读图，仍不能把单页成功等同于完整三页交付。
- D：同一词库覆盖制作单送画布前的图上文字预检与成品回传后的终稿复核。所给 HTML 的 `WORDS_DB` 已静态提取为随公开项目分发的 `content/risk-lexicon.json`，共 990 条、985 个不同词项；运行时不需要原 HTML。两阶段同词多分类合并，保留位置、原类别、风险等级、描述和建议供人工判断；制作单命中未处理不得进入画布成品阶段。终稿看不清的图中文字阻止提交；改制作单、换图或改文案会使对应旧判断失效。原 HTML 的法条说明与“内容合规”结论未经核验，不作为自动结论。
- 词库改为纳入公开包：本地词库和终稿检查默认读取 `content/risk-lexicon.json`；提取脚本默认更新该文件。隔离包测试验证缺少 `runs/` 和原 HTML 时仍能加载全部 990 条并扫描“保录取”。
- `npm test`：28/28；Python 离线测试 14/14（含素材 MCP 与词库解析）；`npm run self-check` 和 `git diff --check` 通过。测试覆盖提交前换图重审、归档失败重试，以及公开包脱离原 HTML 仍可用完整词库扫描。

## 已完成的本地验证

- 独立分享包已包含只读 Teedy MCP、Python 安装器与两个互不覆盖的技能。公开别名文件为空，不带公司特定品牌和校区词。`npm run test:mcp-package` 的隔离用户目录测试 6 项通过；该测试不安装依赖、不连接 Teedy，也不读取真实员工配置。

- `npm test`：12 项通过。覆盖人工来源筛选、无来源时明确确认、排除来源拦截、3—5 页结构、三个 schema 的 JSON 解析与 Codex schema 生成、单线程单任务、成品图顺序与归档审批状态。命令行集成测试从两份模拟参考候选推进至最终图片、文案、待审素材包和批准，核对输出图片、实际使用来源、制作单与 manifest。
- `npm run self-check`：项目必要文件齐全。
- 技能安装脚本以临时 `HOME` 对 Codex 与 WorkBuddy 两种目标目录分别执行，两个落盘 `SKILL.md` 与项目源文件逐字一致。未改动员工真实用户目录。
- Codex CLI 使用 `gpt-6-sol`、`model_reasoning_effort="medium"`、只读沙箱从项目目录读取文件，正确说明了“候选展示 → 人工保留/排除 → `select --human-confirmed` → 制作单校验保存”的流程。该次 CLI 输出曾提示本机模型元数据未找到，使用了回退元数据；不能据此断言所有员工环境的模型配置相同。
- Codex CLI 对一个完全虚构、无历史来源的主题实际生成了 3 页制作单；生成结果经 `validateProductionSheet` 校验通过，来源 ID 为空。初次直接传完整 JSON Schema 时，接口拒绝 `uniqueItems`；现用 `scripts/build-codex-schema.mjs` 生成受支持的输出结构，业务规则继续由本地校验器执行。结构化输出支持部分 JSON Schema 关键字的限制见[官方文档](https://developers.openai.com/api/docs/guides/structured-outputs)。
- 上游内容指南的 MIT 与 MIT-0 许可副本已按固定提交逐字核对。移植范围见 `upstream-content.md` 与 `upstream-state.md`。
